# TravelSplit: архитектура и порядок разработки v0

## Цель v0

Пользователь создаёт поездку, приглашает участников по username, составляет маршрут по дням, хранит билеты и бронирования, ведёт общий список вещей и расходы, смотрит баланс и загружает фотографии. Один пользователь может участвовать в нескольких командах и поездках.

## Границы первой версии

| Входит в v0 | Позже |
| --- | --- |
| Один организатор создаёт поездку и её команду | Повторное использование команды для нескольких поездок |
| Приглашение зарегистрированного пользователя по username внутри сервиса | Письма, push и приглашение человека без аккаунта |
| Принять или отклонить приглашение | Сложная система ролей и передача владения |
| Локальное серверное хранилище и демо-выбор пользователя | Настоящая БД и авторизация |

Команда — группа участников. В v0 при создании поездки автоматически создаётся новая команда. Это делает видимым доступ ровно к этой поездке. Модель допускает несколько поездок в одной команде в будущем, но интерфейс v0 не переиспользует команды: вступление в старую команду иначе могло бы неожиданно открыть другие её поездки.

## Состав системы

```text
React UI ── HTTP/JSON ── Spring Boot API ── сервисы предметной области
                                                │
                                                ├── репозитории (интерфейсы)
                                                │     ├── v0: локальные JSON-файлы
                                                │     └── позже: БД
                                                └── хранилище вложений
                                                      ├── v0: локальные файлы
                                                      └── позже: объектное хранилище
```

Сервер — модульный монолит. Модули: `users`, `teams`, `invitations`, `trips`, `itinerary`, `bookings`, `packing`, `expenses`, `media`. Каждый содержит HTTP-слой, прикладную логику, модель и доступ к данным. Общие правила доступа должны проверяться в сервисах, а не только скрытием кнопок в React.

Фронтенд: общий каркас и маршрутизация; отдельные страницы «Мои поездки», «Приглашения», «Поездка» (вкладки по возможностям), «Создать поездку». Запросы к API и типы данных держать отдельно от компонентов. Для разработки интерфейса использовать реальные ответы локального API либо тестовые fixtures с тем же контрактом.

## Модель данных

| Сущность | Основные поля и связи |
| --- | --- |
| `User` | `id`, `username`, `displayName`, `createdAt`. Username уникален без учёта регистра и после регистрации в v0 не меняется. |
| `Team` | `id`, `name`, `ownerUserId`, `createdAt`. |
| `TeamMembership` | `teamId`, `userId`, `role`, `joinedAt`. Уникальная пара `(teamId, userId)`. Один `userId` может встречаться в сколь угодно многих командах. |
| `Invitation` | `id`, `teamId`, `inviterUserId`, `inviteeUserId`, `status`, `createdAt`, `respondedAt`. Статусы `PENDING`, `ACCEPTED`, `DECLINED`. |
| `Trip` | `id`, `teamId`, `title`, `destination`, `startsOn`, `endsOn`, `currency`, `cover`, `createdAt`. В v0 одна команда создаётся для одной поездки. |
| `ItineraryItem` | `id`, `tripId`, `date`, `time?`, `title`, `location?`, `notes?`, `sortOrder`. |
| `Booking` | `id`, `tripId`, `type`, `title`, `startsAt?`, `endsAt?`, `reference?`, `notes?`, `attachmentIds[]`. Тип: билет, жильё или другое бронирование. |
| `PackingItem` | `id`, `tripId`, `title`, `assignedUserId?`, `completed`, `completedByUserId?`. |
| `Expense` | `id`, `tripId`, `paidByUserId`, `amountMinor`, `currency`, `title`, `spentAt`, `participantUserIds[]`. Сумма хранится целым числом минимальных единиц валюты. |
| `Media` | `id`, `tripId`, `uploadedByUserId`, `kind`, `originalName`, `storageKey`, `uploadedAt`. Метаданные отделены от содержимого файла. |

В API и хранилище связи устанавливаются по внутренним неизменным ID. Username служит только для поиска адресата приглашения. Перед поиском он нормализуется одинаковым правилом на записи и чтении, например `trim` + приведение к нижнему регистру; отображаемый вариант можно хранить отдельно.

## Приглашение и участие в нескольких командах

```text
Создать демо-пользователя → уникальный username
Создать поездку → создать команду → добавить создателя в команду
Пригласить по username → найти User → записать PENDING Invitation
Адресат выбирает свой демо-профиль → видит входящую заявку
Принять → атомарно добавить TeamMembership и пометить ACCEPTED
Отклонить → пометить DECLINED без добавления участника
```

Приглашение запрещено для самого себя, уже состоящего в команде участника и при существующей активной заявке в ту же команду. При принятии заявки нужно повторно проверить статус и отсутствие участника: два нажатия не должны создать две записи. Список «Мои поездки» строится по всем `TeamMembership` пользователя, без ограничения одной командой.

## Без БД и авторизации

Для v0 использовать **локальный JSON-снимок на сервере за интерфейсами репозиториев**, а не состояние только в браузере. Так приглашения, общие списки и расходы будут сохраняться между перезапусками и будут видны разным демо-пользователям. Все сущности хранятся в одном снимке: сервер сериализует изменения, записывает временный файл и атомарно заменяет снимок. Это позволяет принять приглашение и добавить участника одним изменением. Локальный файл остаётся вне Git. Для v0 достаточно одного экземпляра сервера; этот механизм не рассчитан на параллельные серверы.

Создание пользователя в v0 — регистрация демо-профиля без пароля. На клиенте есть переключатель «Сейчас я: Анна / Иван / …»; выбранный `userId` передаётся в каждом запросе, например заголовком `X-Demo-User-Id`. Сервер проверяет принадлежность к команде и право отвечать на приглашение относительно этого ID. Это **не защита от подмены личности**: режим доступен только локально и не должен быть опубликован как полноценный сервис. При подключении авторизации меняется способ получения текущего `userId`, а бизнес-правила и API остаются максимально стабильными.

Начальные фикстуры: минимум три пользователя, две команды/поездки с одним общим участником и ожидающая заявка. Они позволяют сразу проверить сценарий нескольких команд и принятие приглашения.

## API: минимальный контракт

| Операция | Метод и путь |
| --- | --- |
| Создать демо-профиль | `POST /api/users` |
| Получить/сменить профиль в демо-режиме | `GET /api/demo/users`, `GET /api/me` |
| Получить свои поездки из всех команд | `GET /api/me/trips` |
| Создать поездку и её команду | `POST /api/trips` |
| Пригласить по username | `POST /api/teams/{teamId}/invitations` с `{ "username": "..." }` |
| Получить входящие приглашения | `GET /api/me/invitations` |
| Принять/отклонить приглашение | `POST /api/invitations/{id}/accept`, `POST /api/invitations/{id}/decline` |
| Читать/править маршрут | `GET/POST/PATCH/DELETE /api/trips/{tripId}/itinerary...` |
| Читать/править бронирования | `GET/POST/PATCH/DELETE /api/trips/{tripId}/bookings...` |
| Читать/править вещи | `GET/POST/PATCH/DELETE /api/trips/{tripId}/packing-items...` |
| Читать/править расходы | `GET/POST/PATCH/DELETE /api/trips/{tripId}/expenses...` |
| Посмотреть баланс | `GET /api/trips/{tripId}/balance` |
| Загрузить/получить фото и вложения | `POST/GET /api/trips/{tripId}/media...` |

Итоговые конкретные пути и тела запросов следует зафиксировать перед реализацией каждого модуля. Ошибки API должны различать `400` (неверные данные), `403` (нет доступа), `404` (не найдено) и `409` (дубликат или конфликт состояния).

## Расходы и баланс

Для v0 в каждой поездке одна валюта. Расход оплачивает один участник, делится он поровну между выбранными участниками этой же команды. Расчёт долей ведётся в целых минимальных единицах валюты; остаток распределяется детерминированно по ID участников. Баланс участника = оплачено им − его доли всех расходов. Сумма балансов команды должна равняться нулю. Предложенные переводы между должниками и кредиторами вычисляются из балансов, но не считаются совершёнными платежами.

## Порядок работы: вертикальные этапы

1. **Каркас и контракт.** Создать Spring Boot и React проекты, конфигурацию локального запуска, общий формат ошибок, ID и даты; реализовать JSON-репозитории, фикстуры, демо-переключатель пользователя. Проверка: после перезапуска данные остаются, на фронтенде можно выбрать одного из трёх пользователей.
2. **Создание поездки и приглашения.** Демо-регистрация с уникальным username, создание поездки/команды, поиск адресата, входящие заявки, принятие/отклонение, список поездок из нескольких команд. Это первая сквозная история. Проверка: Анна приглашает Ивана, Иван принимает и видит поездку; Иван одновременно видит другую свою поездку; отказ не даёт доступа.
3. **Маршрут по дням.** Дни поездки и элементы маршрута с датой и порядком; проверка попадания даты в интервал поездки. Проверка: два участника видят одну и ту же последовательность после перезапуска.
4. **Билеты и бронирования.** Сначала структурированные записи, затем вложения через общий модуль файлов. Проверка: участник команды может открыть запись и скачать её файл, чужая команда не может.
5. **Список вещей и расходы.** Назначение ответственного и отметки выполнения; запись расходов с выбранными участниками и одной валютой. Проверка: изменения видны всем участникам команды.
6. **Баланс и фото.** Расчёт чистых балансов и предлагаемых переводов; загрузка и просмотр общего фотоальбома. Проверка: сумма балансов равна нулю, фото доступны своей команде и недоступны чужой.
7. **Замена временной инфраструктуры.** Подключить БД и миграции, перенести репозитории; затем добавить регистрацию с паролем/сессию или другой выбранный способ авторизации. Убрать `X-Demo-User-Id` до публичного развёртывания.

Каждый этап заканчивается работающим пользовательским сценарием с UI и API, а не только набором классов. Визуальная тема «утро → день → вечер → ночь» может подключаться параллельно поверх каркаса: она не должна блокировать проверку создания поездки и приглашений.

## Первое практическое действие

Начать с этапов 1–2 как одного небольшого сквозного прототипа: три демо-пользователя, создание поездки, приглашение по username, принятие заявки и список поездок для пользователя в нескольких командах. Эти действия проверят самую важную связь данных; на неё затем опираются маршрут, бронирования, вещи, расходы и фото.
